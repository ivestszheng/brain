# react-turborepo开发实战复盘

## 🌍 项目背景 (Context)
> *写在这里，防止半年后自己忘了当初为啥这么干。*

- **业务目标**：turborepo 技术栈最初是为了响应 CTO 的需求，因为最开始项目在 GitHub 上管理，我们的可创建项目数量受限。
- **技术栈概览**：Turborepo + Changeset + Shadcn/ui + React
- **核心架构决策**：相比于 Nx 等工具庞大且复杂的配置体系，Turborepo 非常轻量。它不强制绑定特定的包管理器（完美兼容 pnpm workspaces），也不做代码生成或版本发布，而是专注于“任务调度 + 内容缓存”。这种低侵入性的设计，使得它非常容易集成到现有的项目中，学习成本极低。

## 🟢 Keep：哪些代码/设计扛住了？
> *别光看Bug，也要看哪里写得漂亮，下次直接抄。*

- **设计亮点**：Tuborepo 这类 Monorepo 框架已经现代中大型前端工程化、以及 AI 辅助开发场景下的主流趋势。
  - 在 AI 辅助开发越来越普及的今天，AI 工具（如 Copilot、Cursor 等）的核心竞争力在于对项目上下文的理解。Monorepo 将业务代码、组件库、工具包、配置文件集中在一个仓库里，AI 可以一次性读取完整的项目信息和依赖关系，给出更准确、可直接运行的代码。相比之下，多仓库模式下 AI 很难感知跨仓库的依赖和版本约束。
  - 对于我个人来说，解决多包管理的通用痛点。避免了重复开发，相同的工具函数、Hooks 不用在多个项目里复制粘贴，改一处全局生效。

## 🟡 Improve：哪里写得烂但还能跑？
> *这是还债，不是重写。*

- **可维护性**：春鹏的部署脚本硬编码了`app`子包中的 `Dockerfile.prod` 与 `Dockerfile.test`，加上需要开发环境的 `Dockerfile.dev`，一个项目需要维护 3 个文件，心智负担太大。
  - **目前方案**：在 `packages` 中增加 `docker` 包，用来存放 `D模板（例如 `模板（例如 `Vite` 项目与 `Next`项目两个模板）。每次通过脚本自动创建 `Dockerfile` 并提交 `Git` 管理。
  - **优化方案**： 最好还是通过 `--build-arg APP_NAME=xxx` 传入变量，避免硬编码。但是目前方案已经解决我的需求，而且不需要后端配合，就这样算了吧。
